# update_cell_conf.sh — смена сети в конфигах ячеек Exadata

Скрипт меняет management-сеть (`eth0`), настройки ILOM, DNS, NTP и таймзону в
XML-конфигурациях ячеек (`/opt/oracle.cellos/cell.conf`). Источники новых
значений — база preconf Oracle OneCommand (CSV). Исходные конфиги не изменяются:
результат всегда пишется в отдельный файл с суффиксом `_new.conf`.

Подменяются ровно эти поля, остальное сохраняется дословно:

| Что меняется в конфиге | Откуда берётся |
|---|---|
| `<Interfaces>` с `<Name>eth0</Name>`: `Gateway`, `IP_address`, `Netmask` | management-сеть строки базы |
| корневые `<Nameservers>` (2 тега) | DNS из базы, первые два адреса |
| корневые `<Ntp_servers>` (2 тега) | NTP из базы, первые два адреса |
| `<Timezone>` и `<ILOM_Timezone>` | таймзона из базы |
| `<ilom>`: `ILOM_Gateway`, `ILOM_IP_address`, `ILOM_Netmask` | сеть ILOM строки базы |
| `<ilom>`: `ILOM_Nameserver` | DNS ILOM, **весь** список через запятую |
| `<ilom>`: `ILOM_First_NTP_server`, `ILOM_Second_NTP_server` | NTP ILOM |

## Состав каталога

| Файл | Назначение |
|---|---|
| `update_cell_conf.sh` | сам скрипт (bash + awk, зависимостей нет) |
| `preconf.csv` | база preconf: по строке на сервер |
| `cell_conf/cell_<hostname>.conf` | исходные конфиги ячеек (только чтение) |
| `cell_conf/cell_<hostname>_new.conf` | результат работы скрипта |
| `cell_conf/sum.md5` | контрольные суммы исходных конфигов |
| `cell_group` | список хостов ячеек по одному в строке — нужен только для scp-шагов, готовится вручную |

## Cбор текущих конфигов со всех серверов группы

Прежде чем обрабатывать конфиги, их нужно собрать с серверов группы (`cell_group`
— файл со списком хостов, по одному в строке):

```bash
for H in `cat cell_group`; do  scp -p $H:/opt/oracle.cellos/cell.conf /root/cell_conf/cell_`echo $H`.conf ; done
```

- `scp -p` сохраняет мету времени исходного `cell.conf`;
- конфиг каждого сервера сохраняется в `cell_conf/cell_<hostname>.conf`
  (например, `cell_ex9scell01.conf`);
- **важно**: скрипт сам выводит это имя из колонки `hostname` базы (колонки `file`
  в preconf нет) — имя файла на диске должно совпадать, иначе строка будет
  пропущена.

## Запуск

**Без параметров скрипт ничего не обрабатывает, а печатает справку** и выходит с
кодом `0`:

```bash
./update_cell_conf.sh                       # только справка, ничего не делается
./update_cell_conf.sh my_base.csv           # своя база, каталог конфигов по умолчанию
./update_cell_conf.sh my_base.csv my_conf/  # база и каталог явно
./update_cell_conf.sh -dry                  # контрольный прогон по умолчанию
./update_cell_conf.sh -dry my_base.csv      # контрольный прогон своей базы
./update_cell_conf.sh --help                # справка
```

- Чтобы начать работу, укажите базу явно: `./update_cell_conf.sh preconf.csv`.
- Опции (`--dry`, `--help`) ставятся в любое место — до аргументов или после.
- Значения по умолчанию берутся **из каталога скрипта**, а не из текущей
  директории: `preconf.csv` и `cell_conf/` рядом со скриптом.
  Запускать можно из любого места — результат не изменится.
- По каждой строке базы печатается статус: `OK` (конфиг записан, ниже — какие
  значения подставлены), `DRY` (строка проверена, файл не тронут), `SKIP` (строка
  не обрабатывается) или `ERROR` (строка отвергнута); дополнительно могут идти
  `WARN` — обработка при этом продолжена. В конце — сводка
  `Итого: обработано N, пропущено M, предупреждений W, ошибок E`.
- Код возврата `0` — ошибок нет. `1` — были ошибки: битый IPv4 или пустое
  обязательное поле в базе, обрезанная строка, сдвиг полей, в конфиге нет блока
  `eth0` или неожиданное число тегов `Nameservers`/`Ntp_servers`, подмена не
  прошла самоконтроль. `2` — неверная командная строка (неизвестная опция).
- Пропуски и предупреждения ошибкой **не** считаются и код возврата не портят:
  строки `node type=dbpp` (у БД-серверов нет `cell.conf`), строки без исходника в
  `cell_conf/`, несмежная маска, единственный адрес в списке DNS/NTP.
- При ошибке строки `*_new.conf` для неё не создаётся — неполный конфиг на хост
  не уедет.
- Повторный запуск идемпотентен: исходник читается заново, выход перезаписывается,
  результат байт в байт тот же.

### Контрольный прогон: `--dry`

`--dry` выполняет всё, кроме записи: разбирает и валидирует базу, подменяет поля,
проходит самоконтроль, но `*_new.conf` не создаёт и не перезаписывает (временный
файл удаляется). Считается как обычный прогон, только в сводке вместо
«обработано» — «проверено», а в конце добавляется строка
`Режим -dry: ничего не записывалось.`

По каждой строке в `DRY`-статусе дополнительно указано, чем закончился бы реальный
прогон:

| Пометка | Значение |
|---|---|
| `(будет создан)` | `*_new.conf` на диске нет |
| `(совпадает с существующим)` | файл есть и меняться не будет |
| `(ОТЛИЧАЕТСЯ от существующего)` | файл есть, после реального прогона он изменится |

Полезный порядок работы: `./update_cell_conf.sh -dry my_base.csv` (посмотреть
значения и ошибки) → `./update_cell_conf.sh my_base.csv` (записать) → раскладка
по хостам.

## Что берётся из базы preconf

База — предконфиг OneCommand формата `11.2.2.1.0`. Служебные строки (сигнатура
`Cell,Preconfig,version,…`, комментарии `#…`, строка заголовка, терминатор из
одних запятых) и пустые строки пропускаются, `CRLF` переносится. Обрабатываются
только строки с `node type=cell`.

**Главная особенность формата:** заголовок описывает лишь первые 17 колонок, а
строка ячейки содержит 28 полей (строка БД-сервера — 34). ILOM-блок заголовком не
покрыт, поэтому колонки сопоставляются **позиционно**, а не по именам:

| № поля | Содержимое | Использование |
|---|---|---|
| 1 | hostname | поиск `cell_conf/cell_<hostname>.conf` |
| 3 | node type | фильтр: `cell` — в работу, `dbpp` — пропуск |
| 8, 9, 10 | ip, netmask, gateway | management-интерфейс `eth0` |
| 15 | nameservers (через пробел) | корневые `<Nameservers>` |
| 16 | ntps (через пробел) | корневые `<Ntp_servers>` |
| 17 | timezone | `<Timezone>` + `<ILOM_Timezone>` |
| 18 | маркер `ilom:` | контрольная точка: нет маркера — в строке сдвиг полей, строка отвергается |
| 20, 21, 22 | ilom ip, netmask, gateway | блок `<ilom>` |
| 23 | ilom nameservers (через пробел) | `<ILOM_Nameserver>` |
| 24 | enabled | не используется |
| 25, 26 | ilom ntp 1, ilom ntp 2 | `ILOM_First_NTP_server`, `ILOM_Second_NTP_server` |

Поля 5–7 (`eth interface`, `eth type`, `mac address`), 11–14 (`bondib …`) и
28–34 (SCAN-блок БД-серверов) на конфиг не влияют.

Списки адресов в базе разделены пробелом. В парные теги `<Nameservers>` и
`<Ntp_servers>` попадают первые два адреса; если адрес один, второй тег получает
тот же адрес. В `<ILOM_Nameserver>` записывается весь список через запятую. Если
поле 26 пустое, второй NTP ILOM получает адрес из поля 25.

## Логика работы

1. **Чтение базы.** Скрипт проходит CSV, отсекает служебные и пустые строки,
   оставляет ячейки, проверяет длину строки и маркер `ilom:` (защита от сдвига
   полей), валидирует значения: непустота обязательных полей, формат IPv4 по
   октетам, разбор списков DNS/NTP по пробелам. Несмежная маска — предупреждение,
   значение пишется как в базе.
2. **Поиск исходника.** Для строки берётся `cell_conf/cell_<hostname>.conf`; нет
   файла — строка пропускается.
3. **Подмена** одним проходом awk, результат — во временный файл:
   - блоки `<Interfaces>` буферизуются до `</Interfaces>` и значения меняются
     только в блоке с `<Name>eth0</Name>` — теги в конфиге отсортированы по
     алфавиту, поэтому `<IP_address>` стоит раньше `<Name>eth0</Name>` и блок
     нужно сначала увидеть целиком; иначе подмена задела бы адреса приватных
     `re0`/`re1`;
   - парные `<Nameservers>`/`<Ntp_servers>` подменяются по счёту встречи: первый
     тег ← первый адрес, второй ← второй;
   - уникальные теги `<Timezone>` и `<ILOM_*>` подменяются напрямую, причём
     `<ILOM_*>` — только внутри блока `<ilom>` и по точным именам тегов;
   - заменяется только значение между тегами: отступы, порядок тегов и все
     остальные строки сохраняются посимвольно; формат переводов строк исходника
     (LF или CRLF) сохраняется — конфиг с `\r\n` останется с `\r\n`.
4. **Самоконтроль по временному файлу.** Результат сверяется с исходником
   (сохранено число строк и число тегов `IP_address`) и с базой (в файле
   присутствует каждая из подстановок). Любое расхождение — ошибка, файл не
   остаётся.
5. **Запись.** Временный файл перемещается в
   `cell_conf/cell_<hostname>_new.conf` (существующий выход перезаписывается).
   В режиме `-dry` вместо перемещения временный файл удаляется, а по строке
   печатается, был бы файл создан, совпал с существующим или отличался от него.
6. **Сводка.** `Итого: обработано N, пропущено M, предупреждений W, ошибок E`
   (в `-dry` — «проверено N»), код возврата — по числу ошибок.
   Прерывание (`Ctrl-C`, `kill`) временный файл не оставляет: он удаляется.

## Основные правила

- Запуск без параметров — это справка, а не работа: файлы не создаются и не
  меняются. Чтобы обработовать базу, укажите её явно.
- Первый прогон по новой базе лучше делать с `-dry`: он показывает, какие значения
  уйдут в какие конфиги, и сразу вскрывает ошибки базы, ничего не записывая.
- Исходные `*.conf` никогда не изменяются: обработка всегда читает исходник и
  всегда перезаписывает `*_new.conf`. Контроль — `cd cell_conf && md5sum -c sum.md5`.
- В работу берутся **только серверы, перечисленные в базе**. Добавили сервер —
  добавьте строку в базу и запустите скрипт; лишние конфиги в `cell_conf/` не
  трогаются.
- Не изменяются: `<Hostname>`, приватные интерфейсы `re0`/`re1` и их адреса,
  `Net_type`, `Version`, структура `Nameservers`, хостнеймы ILOM и все прочие
  поля конфига.
- Формат конфига предполагается таким: один тег — одна строка; ровно два тега
  `Nameservers` и два `Ntp_servers`; один `Timezone`; management-интерфейс —
  `eth0`. Отклонения (нет блока `eth0`, три `Nameservers`, незакрытый блок) —
  ошибка, а не «тихая» подмена.
- Скрипт ничего не отправляет на хосты и не применяет конфиг: он только готовит
  файлы. Применение — отдельный шаг (`cellcli` / `cellipconf`) после раскладки.

## Обратная раскладка новых конфигов на хосты

После обработки готовые `cell_conf/cell_<hostname>_new.conf` раскладываются по
серверам группы — имя файла для каждого хоста вычисляется из `$H` так же, как
при сборе, новое местоположение на хосте — `/root/`:

```bash
for H in `cat cell_group`; do  scp -p /root/cell_conf/cell_`echo $H`_new.conf $H:/root/cell_`echo $H`_new.conf ; done
```

Вариант с пропуском хостов, для которых `_new.conf` не создавался
(например, хоста нет в базе CSV) — иначе scp ругнётся «No such file»:

```bash
for H in `cat cell_group`; do F=/root/cell_conf/cell_${H}_new.conf; [[ -f $F ]] && scp -p "$F" $H:/root/cell_${H}_new.conf || echo "SKIP $H: нет $F"; done
```

Итог на каждом сервере: `/root/cell_<hostname>_new.conf` — исходный
`/opt/oracle.cellos/cell.conf` при этом не трогается.
